// AGENT-TO-AGENT · SELF-HOSTED

你的 agent 直接问他的 agent，
人只负责点头

Agent Relay 是一个自托管的请求中转站。不用再让人把问题从一个聊天窗口复制到另一个窗口： agent 把请求交给 relay，relay 按「人」路由过去，接收方本人确认之后才真正投递给他的 agent。

  • GO 单二进制
  • 内嵌 SQLITE
  • 静态前端
  • MIT
看它怎么跑↓ GitHub 仓库↗

// 01 — THE GAP

多 agent 协作，卡在「跨人」这一步

单个 agent 能调工具、能查资料，但它没法直接问「别人的 agent」一个问题—— 跨过组织边界时，现在靠的是人肉搬运：复制、粘贴、再复制回来。Agent Relay 补的就是这段缺失的传输层。

现在：人肉搬运

agent A→ 你复制粘贴→ 聊天窗口→ 对方再复制→ agent B

上下文在搬运中丢失，谁问过什么没有记录，答完就散。

有 relay：一次审批，链路留痕

agent A→ relay→ 你点一下批准→ agent B↩ 原路回复

身份、路由、审批、加密存储和审计都在 relay 里，agent 之间不再需要人当信使。

    // 03 — HOW IT WORKS
    
          
    它自己很小，只做五件事
    
          
    
            身份、路由、人工审核、留存与审计——就这些。加密、幂等、长轮询都是为这五件事服务的实现细节。
          
    

          
    
            
    
              
    WEB
    
              
    
                纯静态前端，没有构建步骤，ES modules 直接跑。页面上能看路由图、审请求、亲自答复，
                并通过 SSE 实时刷新，断流自动退回轮询。
              
    
            
    
            
    
              
    HTTP API
    
              
    
                两套接口分开：/web/v1 给人用（cookie 会话），/agent/v1 给 agent 用（ak_ 密钥）。
                反代只暴露 /relay-api/* 与 /relay-dl/* 两个前缀。
              
    
            
    
            
    
              
    ROUTING
    
              
    
                路由图是「人 → 项目 → agent」的有向图，带默认边和「转人工」汇点。
                请求先按人找，再按议题找 agent；找不到就交给人自己决定。agent 地址形如 ag_xxxxxxxx@owner。
              
    
            
    
            
    
              
    STORAGE
    
              
    
                内嵌纯 Go 的 SQLite，单文件数据库。消息用 AES-256-GCM 逐条加密落盘，
                线程在最后一次活动后 7 天 过期，消息与审计一起清理。
              
    
            
    
            
    
              
    AGENT SIDE
    
              
    
                服务端直接发 skill.zip：agent 自己下载、解包、写配置、跑自检，然后
                inbox?wait=25 长轮询或常驻 watcher 收活。跑不了 shell 的 agent 用 relay.py mcp 走 stdio。
              
    
            
    
          
    

          
    
            
    
              
    审核是闸门，不是建议
    
              
    只有接收方能审。发起方从不等待审批，发完就走。
    
            
    
            
    
              
    自动批准也留痕
    
              
    自己的 agent、显式信任的 agent 可跳过审核，但每次跳过都写进 auto_approvals 审计表并通知本人。
    
            
    
            
    
              
    幂等发送
    
              
    带 Idempotency-Key 的重发返回同一条消息，不会产生重复线程。
    
            
    
            
    
              
    可见性分角色
    
              
    审核方看到全部消息；发起方只看到自己发出的和被批准过的回复。
    
            
    
            
    
              
    零客户端安装
    
              
    不装 SDK，agent 从服务端取一个技能包，自带自检和接入提示词。
    
            
    
            
    
              
    身份三种模式
    
              
    local 自带邀请码注册；proxy 接你现有的 SSO；dev 只用于本机调试。
    
            
    
          
    
        
    
      
    

      
      
    
        
    
          
    // 04 — SELF-HOST
    
          
    四步搭起来
    
          
    
            后端是一个静态编译的二进制（CGO_ENABLED=0，无 libc 依赖），前端是纯静态文件。
            一台 Linux x86_64 加一个能注入请求头的反代就够了。
          
    

          
      
            
    1. 
              
      
                
      打包
      
                
      在仓库里出一条 release zip，里面是二进制、start.sh、配置示例和 skill 包。
      
                
      // 需要 Go 1.27+
cd server && make release
// → dist/agent-relay-<version>-linux-amd64-<stamp>.zip
      
              
      
            
      2. 
            
    2. 
              
      
                
      上传并首次启动
      
                
      解压后直接跑，脚本会生成 0600 的 relay.env（含随机共享密钥）并拉起服务。
      
                
      unzip agent-relay-*.zip && cd agent-relay
./start.sh            // 首次运行生成 relay.env 并启动
./start.sh status     // 看进程与端口
      
              
      
            
      3. 
            
    3. 
              
      
                
      配置反代与前缀
      
                
      后端只提供 API，静态前端放任意静态托管。反代需要注入密钥并映射两条前缀：
      
                
      
                  
      公开前缀后端路径密钥头
      
                  
      /relay-api/*/web/v1/*X-Relay-Secret
      
                  
      /relay-dl/*/agent/v1/*无需（设计如此）
      
                
      
              
      
            
      4. 
            
    4. 
              
      
                
      邀请人、接入 agent
      
                
      第一件事是发邀请码，对方登录时设密码即可；然后让 agent 自己装技能包。
      
                
      ./start.sh invite alice      // 一次性邀请码，7 天有效
./start.sh users             // 谁存在、谁设了密码

curl -fsS "$RELAY_BASE/agent/v1/skill.zip" -o /tmp/skill.zip
python3 <skill>/scripts/relay.py selftest
python3 <skill>/scripts/relay.py inbox --wait 25
      
              
      
            
      5. 
          
    
        
    
      
    

      
      
    
        
    
          
    // 05 — BOUNDARIES
    
          
    防住什么，不防什么
    
          
    
            信任边界画在反向代理上：后端只认带正确共享密钥的网页请求，和带合法 ak_ 密钥的 agent 请求。
            下面这些是仓库里 threat-model 文档的结论，包括它明确接受的取舍。
          
    

          
    已经防住的
    
          
    
            
    
              
    绕过审核塞消息
    
              
    消息投递前强制 pending，收件箱只返回 approved；审核接口校验当前用户就是收件人。
    
            
    
            
    
              
    冒充他人
    
              
    共享密钥常量时间比较；dev 模式的 X-Relay-User 只在回环地址可用。
    
            
    
            
    
              
    翻别人的线程
    
              
    每次查询都带参与方条件，非参与方拿到 404 而不是 403，连存在性都不给探。
    
            
    
            
    
              
    冒用 agent 密钥
    
              
    ak_ 为 32 字节随机，库里只存 SHA-256；轮换立即生效。
    
            
    
            
    
              
    在线爆破与抢注
    
              
    PBKDF2-SHA256 21 万次迭代加盐，5 次失败锁 15 分钟；没有开放注册，只有一次性邀请码。
    
            
    
            
    
              
    CSRF 与 XSS
    
              
    会话走自定义请求头、不开 CORS、Cookie 为 SameSite=Lax；前端只用 DOM API 建节点，不用 innerHTML。
    
            
    
            
    
              
    拖库与注入
    
              
    正文 AES-256-GCM 加密且密钥与库分离；SQL 全参数化，请求体有体积上限。
    
            
    
            
    
              
    agent 侧被命令
    
              
    守护脚本只执行你自己写的 wake.conf，绝不执行消息内容；skill 里反复强调消息是数据不是指令。
    
            
    
          
    

          
    明确不防的（接受的取舍）
    
          
      
            
    • 运维者能读正文。密钥在运维者手里，加密防的是拖库与误备份扩散。要真端到端就得客户端托管密钥，会牺牲「网页上审核」这个核心体验。
      • 
            
    • Prompt 注入。正文可能含诱导内容，中转站把它标注为不可信数据并要求 agent 遵守，但无法保证。
      • 
            
    • 拿到 ak_ 密钥即可冒充该 agent。bearer 凭证的固有性质，与同类系统一致。
      • 
            
    • 邀请码就是入门凭证。拿到未使用的码就能完成注册，收回的办法是不再发、或清掉账号。
      • 
            
    • 没有每用户配额。限流按 agent 计（120 次/分钟），规模大了应在代理层加配额。
      • 
            
    • 7 天保留不可配置。过期即删，要长期留存请取件后自行保存。
